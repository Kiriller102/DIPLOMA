## 1. Аутентификация и права доступа — следующий приоритет

Сейчас выбор пользователя и `sender_id` доверяются клиенту. Компоненты Auth0 не образуют систему авторизации: проверки токенов на сервере нет. В имеющихся ветках также нет отдельного реализованного User Service, несмотря на название последнего коммита Web.

1. Выбрать один способ входа: подключить имеющийся прототип Auth0 с проверкой issuer/audience/подписи на API либо реализовать локальную регистрацию, хеширование паролей и серверные сессии.
2. Связать внешнюю учётную запись с локальным пользователем; получать отправителя из проверенной сессии.
3. Закрыть чтение истории участниками чата; создание приглашений и изменение участников — правами администратора; редактирование сообщения — его автором.
4. Выключать деморежим при обычной эксплуатации; убрать выбор произвольного пользователя из такого интерфейса.
5. Разделить внутренний CRUD пользователей и публичные данные профиля; не принимать хеш пароля как контракт регистрации.

**Готово, когда:** подмена `sender_id` не меняет автора, неучастник получает 403, запрос без сессии — 401. Проверки одинаковы для REST и gRPC и покрыты интеграционными тестами.

## 2. Шифрование сообщений

Ветка шифрования содержит C++-примитив и benchmark, но сетевого сервиса, режима шифрования, управления ключами и интеграции с Go нет. Значение `AES`/`Kuznechik` в БД само по себе ничего не шифрует.

1. Определить модель: шифрование на сервере для хранения либо сквозное шифрование между клиентами. Это разные требования к доверенной стороне и хранению ключей.
2. Описать версионируемый формат сообщения: алгоритм и режим, идентификатор ключа, nonce/IV, ciphertext, проверка целостности.
3. Для AES использовать стандартную библиотеку Go и AEAD. Для «Кузнечика» сначала выбрать и проверить режим и контроль целостности; не передавать текст произвольной длины прямо в блочный `Encrypt(short*)`.
4. Определить границу C++: отдельный процесс/API либо библиотека через cgo; добавить тесты совместимости и границ буферов. Сохранить контрольный тест RFC отдельно от benchmark.
5. Реализовать генерацию, хранение, выдачу и смену ключей; при необходимости — безопасный перенос существующей истории.

**Готово, когда:** текст не находится в столбце ciphertext, Unicode проходит полный цикл, модифицированный шифротекст отвергается, ключи отсутствуют в репозитории и логах. Ограничения реализации и результаты проверок задокументированы.

## 3. История и интерфейс

1. Добавить явную пагинацию старой истории и ограничить память браузера; текущий клиент постепенно загружает всю историю пакетами.
2. Передавать события редактирования и удаления; текущий long polling отслеживает только новые ID.
3. Добавить управление участниками и профилем в UI, переименование/удаление чата и редактирование своих сообщений после реализации прав.
4. Если понадобится масштабирование, заменить периодические SQL-проверки на уведомления PostgreSQL либо брокер, затем оценить SSE/WebSocket.
5. Определить правила private-чата: число участников и защита от создания одинаковых пар.

**Готово, когда:** чат с большой историей открывается страницами, обновления корректно видны в двух вкладках, число соединений и потребление памяти остаются ограниченными.

## 4. Надёжность и сопровождение

1. Протянуть `context.Context` и сроки выполнения через все прикладные методы и SQL-запросы; сейчас отмена запроса поддержана в long polling.
2. Перевести версии миграций на числовую сортировку перед добавлением `V10`; добавить контрольные суммы. Для ранее развёрнутых Flyway-схем подготовить отдельный проверенный baseline/перенос, не переписывать применённые миграции.
3. Согласовать PATCH/PUT и возможность очищать поля профиля, добавить отдельные DTO вместо передачи моделей БД во все контракты.
4. Убрать устаревшие поля `.proto` через совместимую версию API; `context` и `sent_ad` пока сохранены.
5. Добавить структурированные логи, метрики задержек и ошибок, резервное копирование с проверкой восстановления, ограничения частоты запросов и TLS для внешнего развёртывания.
6. Включить регулярную проверку зависимостей Go/npm и базовых образов; закрепить образы digest при подготовке релиза. Обновления Go-зависимостей выполнять отдельным проверяемым шагом.
7. Расширить тесты на массовую нагрузку long polling, истечение таймаута, разрыв БД, конкурентные изменения участников и завершение сервера с активными запросами.

**Готово, когда:** CI проверяет изменения на чистой БД, обновление и восстановление воспроизводимы, операции завершаются в заданный срок. Базовый запуск через Compose продолжает работать одной командой.

Последовательность: авторизация → выбранная модель шифрования → история/события → подготовка к внешней эксплуатации. До определения требований не стоит выделять дополнительные микросервисы только ради количества процессов.
